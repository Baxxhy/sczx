# 三、阶段A：先修复已发现的统计问题

## A1. 教师独立检查计数

当前 `Insights.vue` 中的 `independentCount` 直接累加满足条件的作答记录。

需要重点验证：

同一名学生针对同一道检查题重复作答，是否会造成教师汇总结果重复计数。

例如：

某学生对同一道题先答错、再答对、再次答对。

系统必须区分：

- 总尝试次数。
- 已作答题目数。
- 独立完成题目数。
- 独立正确题目数。
- 独立正确学生人数。

这些指标不能混用。

建议按 `studentId + taskId + questionId` 建立题目层级的唯一统计键，按业务含义选取首次或最近一次有效作答。

如果需要展示重试过程，应单独统计尝试次数。

对于未核验、获得帮助、历史固定补救及教师人工确认，必须保留不同口径。

不要将多次尝试当成多道独立完成的题目。

## A2. 统计一致性

检查：

- 教师首页。
- 班级学情。
- 单任务学情。
- 学生学习记忆。
- 错题补救结果。

相同含义的指标必须使用一致的定义。

不同含义的指标必须明确说明。

例如：

“独立正确次数”和“已有独立正确证据的知识点数”必须区分。

应建立统一的后端统计口径与自动化测试。

## A3. 时间与版本

对新增统计特别检查：

- 数据库UTC时间。
- 浏览器本地时间。
- 任务发布时间。
- 学生作答时间。
- 教师反馈时间。
- 历史导入记录。
- 跨课时不同版本。

时间范围筛选必须一致。

历史任务应始终使用发布时的题目与知识点快照。

# 四、阶段B：教师班级学情总览

## B1. 班级整体概览

教师进入班级后，应当能够快速回答：

1. 班级有多少名学生？
2. 当前发布了多少项任务？
3. 多少学生已经开始学习？
4. 多少学生已经提交？
5. 哪些学生尚未提交？
6. 哪些学生逾期？
7. 哪些知识点出现较集中的独立错误？
8. 哪些学生需要教师核对？
9. 哪些错题补救后仍未通过独立复测？
10. 哪些补充教学已经完成？

建议页面包含：

- 班级选择。
- 任务筛选。
- 时间范围。
- 学习参与统计。
- 知识点表现。
- 常见错误。
- 待教师处理事项。
- 最近教学干预。

所有数字必须来自有权限的真实学习记录。

不要硬编码演示比例或虚构学生表现。

## B2. 知识点维度学情

基于第十四步已经实现的学习证据，按知识点聚合。

至少展示：

- 有有效证据的学生数。
- 独立正确学生数。
- 有独立错误证据的学生数。
- 需要补强的学生数。
- 缺少充分证据的学生数。
- 已经完成独立复测的学生数。
- 尚待独立复测的学生数。

同一名学生同一知识点内多次作答，应根据指标口径正确聚合。

必须明确分母：

- 全班人数。
- 已分配任务人数。
- 实际作答人数。
- 有有效核验证据人数。

不要把不同分母的比例直接比较。

## B3. 班级共性困难

结合：

- 学生原始作答。
- 独立错误记录。
- 已确认错因。
- 错题知识点。
- 前置知识困难。
- 补救和复测结果。

识别班级内相对集中的问题。

例如：

“有5名学生在等式两边共同运算相关题目中出现独立错误，其中3名尚无独立复测通过记录。”

类似描述必须能对应具体学生与原始证据。

避免输出：

- 本班普遍缺乏数学思维。
- 班级整体理解能力较差。
- 预计考试成绩下降。
- 学生已经完全掌握某知识。

没有充分证据时，明确标记证据不足。

# 五、学生与题目两级分析

## 5.1 学生详情

教师选择一名有权限的学生时，应看到：

- 已分配任务。
- 已提交任务。
- 独立作答。
- 帮助使用。
- 知识点学习状态。
- 原始错误。
- 错题补救。
- 独立复测。
- 教师已有反馈。
- 复习建议。

必须复用现有LearningMemory数据与来源。

不能另外维护一套独立的AI学习画像。

教师点击证据应能够打开原任务、原题或错题详情。

## 5.2 题目维度

针对实际已发布题目，展示：

- 题目内容。
- 来源课时版本。
- 对应知识点。
- 已作答人数。
- 已核验正确人数。
- 已核验错误人数。
- 未核验人数。
- 有帮助记录人数。
- 常见原始错误。
- 学生的实际解释。

不得把同一学生多次提交计为多名学生。

题目统计必须保留历史版本隔离。

## 5.3 教师人工核对

集中展示需要核对的内容：

- 无法自动评分的答案。
- 数学条件不完整的作答。
- 未核验的变式练习。
- 学生提交的解释。
- 学习记忆关联纠正请求。
- 模型生成结果被系统标记有问题的内容。

教师可以：

1. 查看原题。
2. 查看学生原始作答。
3. 查看程序核验结论。
4. 添加人工意见。
5. 确认或退回。
6. 保存操作记录。

不能覆盖原始程序核验和学生答案。

# 六、个性化及班级教学干预

这是本轮最重要的完整业务闭环。

## 6.1 教师选择干预对象

支持：

- 全班学生。
- 指定学生。
- 在某知识点上存在有效困难证据的学生。

针对第三种情况：

系统可以生成候选名单，但教师必须确认后才能发送。

不能将“证据不足”自动归类为“学习困难”。

## 6.2 干预类型

至少支持：

1. 补充讲解。
2. 错题订正。
3. 前置知识复习。
4. 独立复测。
5. 教师补充说明。

优先复用现有 `SupplementalInstruction`、师生消息和课程任务。

教师安排时应当能够：

- 选择知识点。
- 选择学生。
- 选择真实课时或错题。
- 添加说明。
- 设置截止时间。
- 预览。
- 确认发布。

## 6.3 教学案例辅助

教师看到某个共性问题后，可以直接打开第八步教学案例检索。

检索时带入：

- 当前知识点。
- 主要学生困难。
- 相关前置知识。
- 当前年级与学科。

教师选择相关案例后，可以将经验用于补充讲解。

原文来源必须可追溯。

不能自动把模型建议发布为正式教学任务。

## 6.4 干预后效果回看

学生完成补充学习后，教师应当能够查看：

- 哪些学生收到干预。
- 哪些学生已经打开。
- 哪些学生已经提交。
- 哪些学生完成了新练习。
- 新练习是否独立完成。
- 程序核验结果。
- 哪些学生仍需帮助。

必须区分：

“学生提交了补充学习说明”

与

“学生通过了新的独立复测”。

后者需要实际作答证据。

不能因为学生点击完成就宣称干预有效。

# 七、师生问题反馈与管理端

## 7.1 学生问题队列

当前 `Issues.vue` 主要展示最近的一条问题。

本阶段完善为真正可用的问题队列。

支持：

- 多条问题。
- 问题提交者。
- 来源课程或任务。
- 创建时间。
- 待处理状态。
- 已回复状态。
- 已关闭状态。
- 教师回复历史。

一个学生可以提交多条问题。

教师只能处理自己有权限查看的学生问题。

管理员按既有职责查看系统相关反馈，不得借此读取无关学生私人学习资料。

## 7.2 问题状态

建议：

- 待处理。
- 处理中。
- 已回复。
- 已关闭。

每次状态变更记录：

- 操作人。
- 操作时间。
- 操作内容。
- 原状态。
- 新状态。

保留已有问题及回复。

不能因为升级新的反馈系统而删除历史问题。

## 7.3 管理端日常操作

调查并完善以下已有功能：

- 教学案例审核和发布。
- 资料来源核对。
- 案例修订。
- 教学内容问题反馈。
- 模型失败任务查看。
- 模型失败后的权限校验和手动重试。
- 账号和基础运行状态。

重点改善管理操作的完整性及异常状态。

不重复开发案例管理或模型控制台。

## 7.4 失败模型任务

管理员和相关业务用户应当能够查看：

- 失败任务类型。
- 任务提交时间。
- 失败原因。
- 重试次数。
- 当前状态。
- 是否允许重试。

需要校验：

- 重试时当前业务权限是否仍然有效。
- 任务来源是否已经撤回。
- 课时或案例是否已经失效。
- 重试是否会产生重复的业务数据。

不能通过管理端绕过已有权限限制。

# 十二、必须完成的三条端到端业务流程

## 流程一：发现班级共性困难并安排复习

教师进入A班 → 查看知识点分析 → 发现多个学生在等式性质相关题目上存在独立错误 → 打开原始证据 → 选择对应学生 → 检索相关教学案例 → 发布补充讲解 → 学生收到任务 → 完成实际练习 → 教师查看干预后结果。

必须证明所有统计都有真实数据依据。

## 流程二：单个学生的学情纠正与补救

学生在两道题上出现错误 → 学习记忆生成需要补强建议 → 教师查看具体作答 → 确认一个知识点关联存在问题 → 提交修订并保留审计 → 指定补救 → 学生完成独立新题 → 教师查看新状态和历史记录。

不得覆盖原始答案和程序核验结果。

## 流程三：学生反馈与管理处理

两个学生分别提交不同学习问题 → 教师查看本人有权限的问题队列 → 回复其中一条 → 保留另一条待处理 → 管理员查看需要管理处理的业务问题或失败任务 → 完成对应操作 → 学生重新登录查看状态。

必须证明不同学生和不同教师的数据隔离有效。

# 十三、返修和停止规则

本轮最多两轮实质性修复。

第一轮：

1. 阅读代码。
2. 修复已确认的统计问题。
3. 实现学情分析。
4. 实现教学干预闭环。
5. 完善管理端。
6. 执行初验。

第二轮：

1. 汇总真实失败项。
2. 修复P0/P1。
3. 重新运行相关测试。
4. 完成三条业务流程。
5. 统一终验。

终验后：

- P0/P1全部解决且核心功能通过：第十五步完成。
- 存在P0/P1：保持第十五步未完成。
- 仅有P2/P3：记录待办，不无限返修。
- 环境无法执行：保留阻塞证据。

不得删除失败测试、修改原始结果或降低验收标准。

# 十四、最终交付物

必须交付：

1. 第十五步使用与实现说明。
2. 教师学情统计口径说明。
3. 班级与知识点分析设计。
4. 教学干预业务流程说明。
5. 问题反馈与管理端设计。
6. 必要的数据库迁移说明。
7. 第十五步32项统一验收表。
8. 三条真实端到端业务记录。
9. 跨教师及跨学生权限测试。
10. 自动化测试日志。
11. 桌面三种宽度截图。
12. 原始数据保护检查。
13. 未解决问题清单。
14. README与当前进度更新。
15. 第十六步是否可以开始的明确判断。

最终报告必须明确：

- 哪些功能本来已经存在。
- 哪些功能是本次新增。
- 修复了哪些确定存在的问题。
- 每个统计指标采用什么分母。
- 共性困难依据哪些原始作答。
- 教师干预是否真实送达学生。
- 干预后是否产生新的独立作答。
- 教师与管理员的权限是否正确。
- 哪些结果只是规则或模型建议。
- 哪些问题仍需要人工核对。

按仓库已经存在且仍有效的提交、推送授权执行。提交前先确认本地与远程差异；禁止强制推送、覆盖其他修改或上传测试凭据。

**本阶段最终目标：教师能够从真实班级学情发现教学问题，依据原始学习证据安排补充教学，并看到学生完成后的实际学习记录。**

不要提前实施第十六步完整单元上线。
