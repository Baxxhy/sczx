### 3. 技术与工程约束

前端坚持 Vue 3 + JavaScript，使用现有 Vite、Vue Router、Pinia、shadcn-vue、Reka UI、Tailwind、Lucide、motion-v 和 VueDraggable。业务源码采用 `.vue`、`.js`，不引入 React、TypeScript 或重复组件体系。

建立一个模块化 FastAPI 业务服务，业务数据库只用 MySQL。建议采用 SQLAlchemy 同步访问、PyMySQL、Alembic 和 Pydantic；先检查环境和适用版本，再依据官方文档确定依赖。采用 CPU 可运行的简单部署方式，按当前项目规模组织模块。

教学、数学计算和后续检索预留清楚的 Python 模块边界。外部模型通过 API 适配器接入，保留 ApiPoolProvider 的配置思路；检查可复用代码的来源和兼容性。第四步只建立适配边界及未配置反馈，模型的实际能力接通属于第五步。前端只渲染既定组件或 VisualizationSpec，不执行模型返回的 JavaScript。

开发和验收使用独立 MySQL 数据库。保护已有学生资料、原图和数据库。不要执行清空已有数据库或覆盖原资料的初始化脚本。按用户要求控制工程复杂度，可靠的保存、恢复和错误反馈必须实际可用。

### 4. 建立数据结构与迁移

先列出实体关系和前端旧字段到服务端字段的映射，再建立表、迁移和初始化数据。

至少覆盖账号与角色、班级与成员、课程与课时、案例及发布内容、教案草稿、任务与发布快照、学生任务记录、作答尝试、求助记录、错题、补救记录、教师反馈。同步盘点当前页面中的收藏、消息、问题反馈、内容草稿及管理运行记录，明确其持久化方式；没有真实后台任务的状态须标注示例。

每个主要实体有稳定 ID、必要的关联字段、状态及创建/更新时间。作答、求助、错题和补救关联学生、任务、题目与当前尝试；教师反馈关联对应学生的任务记录。固定参考学生与实际账号产生的数据分别呈现。

教师发布时保存目标、活动、题目及必要关联的快照。随后编辑只改变草稿，重新发布创建新任务；原任务和学生记录继续使用原快照。通过数据库事务处理发布和提交等关联写入，防止部分成功后页面出现断链。对重复发布和重复提交采用简单、可解释的去重规则。

版本迁移有明确命令，首次初始化可重复执行且不覆盖已编辑数据。种子只包含实际能使用的一元一次方程首课、明确标注的案例、演示账号及班级。公开来源尚未核实的内容标注待核对，不编造教师背书。

### 5. 完成账号、登录与班级基础

实现用户名和密码登录、当前用户读取、退出，以及学生、教师、项目管理角色的基础操作范围。演示账号由初始化创建，密码通过环境或初始化流程设置，不在交付报告中暴露凭据。

建议使用后端会话与同源 Cookie，优先借助现有能力完成。前端开发使用 Vite API 代理，部署说明提供相同访问路径。登录失效后给出可恢复的重新登录入口，避免跳转或身份变更把未保存输入静默丢弃。

教师能够创建班级并添加已有学生账号、查看成员；学生任务按班级成员关系查询。首版账号创建由管理端或受控初始化完成，注册找回等账号运营流程后续扩展。原空间切换入口按确认后的真实角色规则调整。

### 6. 完成文件保存与原图关联

提供上传、文件信息读取和页面访问方式。原始题图作为文件保存，MySQL 保存文件 ID、原文件名、类型、存储位置和业务关联。选图后立即上传，成功返回可复用文件 ID；页面通过返回的资源地址显示。

原答案、错题和补救能够回看同一张原图。文件写入失败或业务保存失败要能重试，不能显示“已保存”却找不到文件。重启服务后仍可读取。数据库更新与文件写入采用符合本地存储规模的简单失败处理，不因清理演示而误删原图。

### 7. 接通真实业务接口

按现有页面动作设计清楚的列表、详情、保存和状态变更接口，统一错误结构与前端错误映射。接口应覆盖：登录与当前用户、班级成员、课程和课时、案例草稿与发布、教案保存与预览所需数据、任务发布与详情、学生进度与草稿、作答与求助、提交与错题、补救、学情及教师反馈，以及当前管理端实际需要保存的内容。

管理端发布的案例进入教师列表与详情，教师保存的教案刷新后能重新读取，发布任务进入对应学生列表。教师学情从真实学生记录计算，保存反馈后学生可读取。统计来源必须能追溯到当前任务记录。

固定演示题的结果使用与其适用范围一致的程序判定，必要时使用 SymPy 核对。服务端决定任务提交状态及持久记录，页面展示判定范围。自定义题图只完成保存和关联时，不显示为已经 OCR 或智能批阅。

### 8. 改造前端数据服务和保存机制

先检查现有 platformService 只有聚合 load/save/reset/publishLesson，而很多业务动作直接修改 Pinia 数据的事实，列出必须拆出的业务读写方法。新增 API 请求层和对应业务服务，让页面与状态通过业务方法访问后端。

不要简单地把整个浏览器平台对象作为一个 JSON 大字段反复上传覆盖。可以为首屏提供聚合读取接口，但保存按教案、任务记录、作答、反馈等实际业务边界完成。

调整 `main.js` 的全局深度自动保存及 pagehide 同步写入机制，避免它们继续把登录账号和跨角色服务端数据混在同一个浏览器对象中。按需要保留节流后的草稿保存与失败重试；显示真实保存结果，页面跳转和提交前处理待保存数据。失败时保留输入，恢复网络后允许重试。

业务记录以服务器数据为准。真实 API 模式失败时显示错误与重试，不静默回退成演示成功。若保留独立演示模式，必须明确标识且与真实数据隔离。界面无需显示内部实现说明。

### 9. 处理旧浏览器数据

保留现有浏览器记录的读取与导出能力。依据确认后的迁移规则提供显式导入，先展示数据数量与关联目标，确认后导入隔离数据库。服务端处理 ID 映射与重复导入，保留任务快照、作答、求助、错题、补救、反馈及能恢复的原图。

旧数据缺少来源或无法对应真实用户时，将其作为标明来源的演示历史处理，不将固定示例冒充真实学生表现。导入失败保留原记录，给出失败项；再次导入已有内容不会重复生成记录。普通登录与首次启动不得自动覆盖数据库或删除浏览器历史。

重置只作用于明确约定的演示范围，保留清楚的后果提示及确认。真实学习记录的删除行为按实际产品规则处理。

### 10. 完善运行与页面状态

提供后端依赖、环境变量示例、MySQL 连接、迁移、初始化、文件目录和前后端启动说明。明确基础存活与数据库可用状态，缺少配置时显示可执行的解决信息。前端刷新及直接打开详情路由能够恢复当前用户和对应记录。

保留当前文字对比度与响应式修复：桌面课程页课程介绍与课时目录并排，手机上下排列；不再让少量文字占据巨大的空卡片。新登录、班级和上传界面沿用现有设计，减少辅助文案，保留表单标签、可访问名称、焦点及必要的后果提示。

逐项处理加载、无数据、保存中、保存失败、上传失败、记录不存在、登录失效、重复提交与重试。错误来自真实 API 或可控的隔离故障演示，不将虚假成功作为失败恢复。

### 11. 验收与交付

先写出第四步实施计划和验收清单，再完成实现。遵循项目不保留测试文件、样例、测试配置及专用测试依赖的约定；通过实际 API 调用、隔离数据库查询、浏览器操作与构建收集证据，临时检查脚本放在工作区外。

验证教案修改不改变已发布快照，新发布任务记录独立；刷新、退出重登和后端重启后，数据库及文件均能恢复。两个会话的联动应来自服务端。验证文件回看、旧数据重复导入、无效记录、真实接口失败与重试，不仅检查 HTTP 200，还核对 MySQL 中的实际关联与字段。

## 关键问题的推荐回答

下列内容可用于回答执行者的访谈。问题依赖仍应按 grilling 分轮处理，不要求第一轮一次问完。

1. **第四步做到哪里？** 推荐：完成现有首课流程的真实持久化和跨会话师生联动。原因：可立即证明后端基础支持当前产品使用，范围对应第四步。
2. **登录采用什么方式？** 推荐：用户名密码、后端会话、同源 Cookie；初始化学生、教师和管理账号。原因：符合网页端使用方式，便于真实区分各人的记录。
3. **第一轮支持多少班级和学生？** 推荐：实体支持多班级、多学生，验收先用一个班级和一名学生，再补验第二名学生的记录独立。原因：避免把原演示学生写死为平台唯一用户。
4. **采用什么后端结构？** 推荐：单个模块化 FastAPI 服务、MySQL、SQLAlchemy 同步访问、PyMySQL、Alembic、本地文件目录。原因：依赖清楚，可直接完成数据保存和版本更新。
5. **已发布教案允许直接改吗？** 推荐：延续第三步快照规则；草稿可改，重新发布新建任务，历史任务保留原内容。原因：学生作答与教师反馈必须对应当时学习的内容。
6. **本轮调用真实模型吗？** 推荐：只准备 API 适配边界，演示指导保持明确标识；第五步完成实际调用。原因：第四步先验证数据基础，避免把预设内容包装成模型输出。
7. **旧浏览器记录怎么处理？** 推荐：保留导出，提供显式、可重复去重的导入；不自动覆盖。原因：既能继续使用已有资料，又能辨认演示历史与真实记录。
8. **图片怎么存？** 推荐：后端本地持久目录保存原文件，MySQL 保存文件元数据与关联。原因：当前单服务规模足够使用，原图可跨会话恢复。
9. **班级和账号怎么创建？** 推荐：教师建班、添加已有学生；账号先由管理端或初始化创建。原因：能完成教学流程，账号运营功能可按后续需求增加。
10. **原来的空间切换怎么处理？** 推荐：真实模式展示当前账号可用空间；跨身份验收使用不同账号及独立浏览器会话，开发演示另行标识。原因：避免把本地角色切换误当成真实师生联动。
11. **后端断开时怎么办？** 推荐：保留当前输入并显示保存失败，允许重试；读取失败展示明确的重试入口。原因：用户可以知道哪些记录真正保存成功。
12. **什么才算交付完成？** 推荐：完整首课流程通过真实接口写入 MySQL，两个浏览器会话能互相看到关联变化，重启恢复、原图回看、失败重试及前端构建均有实际证据。原因：能证明页面、接口、数据库和文件已经共同工作。
