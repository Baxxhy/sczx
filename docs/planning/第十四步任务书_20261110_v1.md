# 三、第一阶段：统一学习证据

这是第十四步最重要的基础工作。

## 3.1 学习证据来源

必须支持以下事实来源：

1. 学生原始作答。
2. 作答对应的知识点。
3. 题目数学核验状态。
4. 是否独立作答。
5. 使用帮助的记录。
6. 实际错题。
7. 错因的人工确认状态。
8. 补救练习记录。
9. 独立新题复测结果。
10. 教师人工核对与反馈。
11. 当前任务和课时版本。
12. 对应时间戳。

这些数据应该能够追溯到真实原始记录。

不要仅保存“学生掌握程度良好”这种无法核查的自然语言结论。

## 3.2 统一证据结构

建议形成标准化证据对象：

```json
{
  "evidenceId": "evidence-example",
  "studentId": "student-example",
  "knowledgeId": "kp-equality",
  "sourceType": "independent_attempt",
  "sourceId": "attempt-example",
  "taskId": "task-example",
  "lessonVersionId": "version-example",
  "verification": "verified_correct",
  "helped": false,
  "occurredAt": "2026-11-10T12:00:00Z"
}
```

以上为设计示例，不代表数据库已存在该结构。

至少支持以下证据类型：

- 独立正确。
- 独立错误。
- 接受帮助后的正确。
- 接受帮助后的错误。
- 未核验作答。
- 独立复测通过。
- 独立复测未通过。
- 教师确认。
- 教师指出的问题。

一个原始事件不得因为重复计算或重复运行任务而生成多条等价证据。

证据必须具有稳定ID和原始来源。

## 3.3 原始记录不可变

以下数据必须保持不变：

- Attempt原始答案。
- 原始解题解释。
- 原题内容及其版本。
- HelpRecord。
- WrongQuestion。
- RepairAttempt。
- 原始程序核验结果。

教师或学生对系统推断有异议时，应增加纠正记录或修订解释。

不得直接修改历史事实来使新的掌握状态看起来正确。

# 四、第二阶段：知识点学习状态

## 4.1 状态模型

不建议一开始就输出0—100的“掌握度”。

建议采用有明确证据依据的学习状态：

1. 暂无证据。
2. 证据不足。
3. 需要补强。
4. 正在改善。
5. 已有独立正确证据。
6. 需要再次复习。

这些状态属于系统依据规则给出的学习建议性判断。

不能被描述为确定的学生认知诊断。

## 4.2 计算因素

至少考虑：

- 对应知识点的有效作答次数。
- 独立正确次数。
- 独立错误次数。
- 帮助后的正确次数。
- 独立复测结果。
- 最近一次表现。
- 作答时间分布。
- 教师核对情况。
- 证据数量是否足够。
- 数学核验是否可信。

不能将所有正确作答视为同等证据。

例如：

学生A：接受完整提示后答对一次。

学生B：在不同时间独立答对三道相关题。

两者应当呈现不同的证据情况。

但也不能据此直接推断学生B已经永久掌握。

## 4.3 证据不足时如何处理

当存在以下情况时：

- 只有一次作答。
- 只有模型建议。
- 只有未核验答案。
- 缺少知识点关联。
- 只有旧固定补救记录。
- 缺少独立作答记录。

系统不能直接输出“已掌握”。

应明确显示：

“目前还缺少足够的独立练习证据。”

同时提供可以补充证据的下一步操作。

## 4.4 时间因素

学习状态需要考虑时间。

但是不能任意使用所谓遗忘曲线公式，将学生知识状态自动衰减。

本阶段推荐采用透明的规则：

- 最近刚练习：无需立即重复。
- 一段时间未复习：建议再次检查。
- 近期连续错误：优先补强。
- 接受帮助后正确：建议独立复测。
- 多次独立成功：降低短期复习优先级。

具体时间阈值应可配置，并通过隔离测试验证。

不要宣称该规则已经经过真实教育实验验证。

# 五、第三阶段：跨课时学习记忆

目前学生指导主要围绕当前StudentRecord构建上下文。

第十四步需要让系统在新的课时中合理利用已有学习记录。

## 5.1 跨课时检索

当学生开始新的教学任务时：

1. 读取当前课时知识点。
2. 查找一层前置知识。
3. 查询学生在这些知识点上的历史证据。
4. 选择少量与当前任务真正有关的记录。
5. 根据证据判断是否需要补基础。
6. 在适当情况下向学生提供补充建议。

不能将该学生全部历史聊天记录塞给模型。

## 5.2 记忆选择

建议优先读取：

- 当前知识点近期的独立错误。
- 最近一次独立复测。
- 当前知识点的已确认错因。
- 相关前置知识的有效作答。
- 教师明确确认的反馈。

对于证据不足的知识点，不能虚构学习画像。

需要给每条记忆保留：

- 来源ID。
- 发生时间。
- 关联知识点。
- 是否经过程序核验。
- 是否为教师人工确认。
- 与当前任务的关联原因。

## 5.3 上下文长度

建议：

- 只读取当前相关知识点和一层前置知识。
- 每次最多返回有限数量的有效证据。
- 先以结构化摘要参与决策。
- 必要时读取原始详细记录。
- 不重复发送完整历史题图、全部对话或无关课程记录。
- 不超过现有模型输入预算。

如果没有相关历史证据，正常使用当前课时上下文即可。

## 5.4 记忆与当前回答冲突

如果学生当前回答与历史表现矛盾：

应优先保留当前最新证据，并显示历史记录。

不能强行解释为“学生退步”或“学习能力不足”。

模型不得因为学生过去做错过一道题，就一直按能力较弱的学生来回答。

# 六、第四阶段：个性化复习推荐

这是第十四步核心业务价值之一。

## 6.1 推荐类型

至少支持：

- 补充前置知识。
- 重新查看课时讲解。
- 复习相关教学例题。
- 完成一道新练习。
- 进行独立复测。
- 继续之前未完成的补救。

推荐必须能够直接跳转到真实存在的内容或任务。

不允许生成一个不存在的课程链接。

## 6.2 推荐优先级

建议按照以下规则：

第一优先级：

已经出现明确独立错误，且相关知识点缺少有效复测。

第二优先级：

学生在补救中接受帮助后答对，但没有独立新题证据。

第三优先级：

当前课时依赖的前置知识存在明确困难证据。

第四优先级：

近期需要复习但没有新的检查记录。

第五优先级：

学生主动选择复习的知识点。

推荐时应该明确：

- 为什么推荐。
- 依据哪些作答。
- 需要做什么。
- 完成后如何判断结果。
- 推荐关联到哪个知识点。

## 6.3 推荐去重

同一知识点不应该出现多个内容相同的推荐。

同一错误不能在每次页面刷新后重新生成一条独立推荐。

重复打开页面不应导致推荐任务不断增加。

建议首先采用规则推荐，确保可解释、可复现。

不需要每次刷新学生首页都调用Codex。

## 6.4 推荐结果

建议每条推荐包含：

```json
{
  "knowledgeId": "kp-equality",
  "reason": "相关练习曾出错，补救后尚无独立新题通过记录",
  "action": "independent_retest",
  "targetType": "wrong_question",
  "targetId": "wrong-example",
  "evidenceIds": ["evidence-example"]
}
```

具体字段与现有代码保持一致。

任何推荐都必须有真实有效的目标。

## 6.5 学生操作

学生能够：

- 查看推荐。
- 阅读推荐原因。
- 打开对应课程或错题。
- 开始复习。
- 完成相关练习。
- 返回学习记忆页面。
- 查看新增证据是否改变了推荐状态。

允许学生暂时忽略或稍后处理推荐。

不得因为用户忽略推荐就认定其不愿学习或缺乏主动性。

点击知识点后显示：

1. 当前状态。
2. 关联课时。
3. 主要前置知识。

5. 错题与补救记录。

7. 状态变化过程。
8. 当前复习建议。

每条证据应允许打开对应的原任务或错题。

不能只显示AI生成的总结文字。

## 7.3 复习计划

学生应该能够看到：

- 建议优先复习的知识点。

- 清晰的知识列表。
- 状态说明。
- 证据时间线。
- 简洁的复习入口。
- 可展开的原始依据。

桌面宽度必须检查：

- 1440px。

# 八、第六阶段：教师查看与纠正

教师需要能够了解学生在哪些知识点上需要进一步练习。

但是必须区分：

- 原始事实。
- 程序计算状态。
- 模型建议。
- 教师人工判断。

## 8.1 教师端查看

教师可查看自己有权限的班级学生：

- 知识点状态。
- 独立作答证据。
- 主要错误记录。
- 补救与复测情况。
- 当前系统推荐。
- 教师已确认的反馈。

对不属于自己班级或没有有效业务授权的学生，不能查询个人学习记忆。

跨班学生的记录需要依据实际权限过滤。

教师不能借助学习记忆接口读取其他教师班级的私人学习数据。

## 8.2 人工纠正

教师可以：

- 标记某个系统判断需要复核。
- 补充教学观察。
- 纠正明显错误的知识点关联。
- 对补救结果提出意见。
- 指定实际需要的复习内容。

学生也可以对明显错误的记录或知识关联提出纠正请求。

所有纠正均需要记录：

- 原判断。
- 修订内容。
- 操作人。
- 操作时间。
- 修订原因。

不能覆盖原始学生答案或原始数学核验。

## 8.3 防止过度判断

教师页面不得直接输出：

- 学生学习能力差。
- 学生完全不掌握该知识。
- 该学生未来考试一定会失败。
- 系统已经准确诊断学习障碍。

只允许输出有证据依据的学习状态和教学建议。

# 十二、必须完成的三条完整业务流程

## 流程一：跨课时学习记忆

学生在课时A做错一道题。

经过补救后仍没有独立通过记录。

之后进入课时B，课时B涉及相同知识点。

系统应当：

1. 读取当前课时知识点。
2. 查找学生有关的历史证据。
3. 发现相关补救仍缺少独立复测。
4. 给出适当的复习建议。
5. 允许学生打开原错题。
6. 完成独立新题。
7. 更新学习状态。
8. 返回课时B继续学习。

必须证明整个流程不跨学生串用数据。

## 流程二：前置知识补救

学生在知识点B的课程中遇到困难。

知识点A是B的前置知识。

系统发现学生在A上有明确的历史困难证据。

应当：

1. 展示为什么推荐补A。
2. 查看原始作答依据。
3. 提供相关课时或练习入口。
4. 完成补基础活动。
5. 保存新的学习证据。
6. 返回原来的B知识点课程。

不能仅凭一次错误就认定学生完全没有掌握A。

## 流程三：教师核对与状态纠正

系统给某学生生成学习状态。

教师查看对应证据后认为需要修订知识点关联或解释。

系统应：

1. 展示原始证据。
2. 允许教师提出纠正。
3. 保存修订理由。
4. 保留原始记录。
5. 更新相关状态或推荐。
6. 学生重新进入时看到适当的最新结果。
7. 历史审计记录仍可查看。

必须验证跨教师权限。

# 十三、效果评价

至少比较三个方案：

B0：只依据最近一次作答生成下一步建议。

B1：聚合同一知识点的多次证据。

B2：加入帮助状态、独立复测、前置知识和时间信息。

使用相同的固定数据集和人工定义的预期结果。

重点报告：

- 推荐是否有事实依据。
- 推荐目标是否真实存在。
- 是否正确区分帮助与独立作答。
- 是否错误地将证据不足标记为掌握。
- 是否错误利用其他学生数据。
- 是否重复推荐。
- 是否能够更新状态。
- 不同规则产生的推荐差异。

建议使用人工构造的确定性测试数据验证规则正确性，再用真实模型或实际业务流程验证整体可用性。

不要用模型给自己的推荐打分后宣称准确率提升。

没有真实教育评价时，不得宣称提高学生学习成绩。
