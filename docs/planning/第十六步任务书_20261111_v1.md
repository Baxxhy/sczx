# 三、阶段A：完整单元内容核查与建设

## 3.1 首先盘点真实数据库

代码当前预置：

- `lesson-equation`：等式性质。
- `lesson-simple`：解简单的一元一次方程。
- `lesson-application`：用方程解决生活问题。

后两项在种子代码中是空草稿。

必须先查询实际数据库，确认：

- 哪些课时已经由用户编辑。
- 哪些课时已经发布。
- 哪些课时仅有空草稿。
- 哪些内容已有人工审核。
- 哪些课时关联真实案例。
- 哪些题目已有学生历史作答。
- 哪些内容仍然是自编演示。

不得用新生成内容覆盖已有正式课时。

## 3.2 确定完整单元范围

围绕现有“一元一次方程”单元，形成完整内容覆盖。

至少需要涵盖：

1. 等式性质及其适用条件。
2. 简单一元一次方程的求解。
3. 包含必要变形步骤的方程求解。
4. 一元一次方程在实际问题中的应用。
5. 单元复习及综合检查。

实际课时数量以已有课程结构、内容覆盖和审核结果为准。

不得仅为了达到某个课时数量而机械拆分。

如果需要新增课时，使用现有课程和课时管理接口。

## 3.3 每个课时必须具备

- 课时名称。
- 教学目标。
- 对应知识点。
- 必要前置知识。
- 完整讲解。
- 典型例题。
- 可执行的教学活动。
- 随堂练习。
- 独立检查题。
- 正确参考答案。
- 数学核验状态。
- 教师备课所需提示。
- 必要的案例或资料来源。
- 版本及审核记录。

不得生成只有标题和几段说明的空壳课时。

## 3.4 内容质量要求

所有课时必须满足：

- 同一知识点的定义保持一致。
- 前一课已引入的概念可以在后一课正确使用。
- 前置关系不存在循环。
- 例题难度有合理递进。
- 讲解和练习相对应。
- 练习内容与教学目标相对应。
- 独立检查能够提供真实作答证据。
- 单元复习包含跨课时知识联系。

严禁明显的AI套话和系统元话语。

不要反复使用“通过多元化方式有效提升学生综合能力”等没有具体教学意义的表述。

生成内容必须符合真实教师备课习惯。

## 3.5 来源与审核

所有新增内容必须区分：

- 真实教学材料及可追溯出处。
- 项目自编教学内容。
- AI辅助生成内容。
- 教师确认后的正式内容。

不得把自编教学活动包装成真实教师经验。

正式发布前必须经过现有人工核对流程。

未经明确审核的内容保留草稿状态。

# 四、阶段B：数学正确性专项验收

本阶段属于发布前阻断项。

## 4.1 已发现的具体风险

第十五步实际Codex输出中，讲解等式共同变化时，未在同除规则中明确限制除数非零。

该结果的数学核验状态为 `unverified`。

需要检查课程正式内容、AI讲解、生成教案及变式题中的类似表达。

## 4.2 必须覆盖的数学检查

至少验证：

1. 等式两边同加相同的数。
2. 等式两边同减相同的数。
3. 等式两边同乘相同的数。
4. 同除非零数的条件。
5. 不能除以零。
6. 同乘零导致方程信息丢失。
7. 方程移项与运算依据。
8. 去括号。
9. 去分母时的条件与运算。
10. 负数与分数系数。
11. 实际问题中的设元与列方程。
12. 代回原方程验算。
13. 无法自动验证的文字应用题。
14. 条件不足或没有唯一解的情况。

必须同时检查例题答案、生成的指导文本和独立检查题。

程序可以可靠核验的内容，必须使用已有数学核验工具。

程序无法覆盖的条件性数学陈述，必须进入人工核对。

**不得因为模型返回了合法JSON，就判定数学内容正确。**

已确认的错误不能进入正式发布版本。

# 五、阶段C：跨课时完整学习闭环

学生必须能够从单元入口连续完成多个课时。

## 5.1 单元学习流程

完成：

单元目录 → 第一课 → 随堂活动 → 独立检查 → 下一课 → 前置知识复习 → 应用题 → 单元复习 → 单元学习记录。

重点验证：

- 单元和课时顺序正确。
- 当前课时可准确打开。
- 课程内容与已发布版本一致。
- 学习进度正确。
- 已完成课时不会在刷新后丢失。
- 不同课时的帮助记录互相隔离。
- 同一知识点可以跨课时聚合学习证据。
- 返回上一课时不破坏当前草稿。
- 单元复习使用实际有效的题目。

## 5.2 学习助手

每个课时都应验证：

- 文字提问。
- 题图OCR及确认。
- 提示。
- 举例。
- 换讲法。
- 补基础。
- 自主尝试。

需要特别验证：模型指导是否使用当前课时和当前题目，不能因为之前主要测试“等式性质”而在应用题中仍然回答天平问题。

## 5.3 错题补救

必须至少在三个不同课时中产生真实错题。

验证：

- 错题自动记录。
- 错因分析。
- 原始作答保留。
- 分步补救。
- 相关变式题。
- 数学核验。
- 独立复测。
- 返回原课时。
- 教师查看补救结果。

不同课时不得共享错误的题目上下文。

## 5.4 学习记忆

验证：

- 相同知识点跨课时证据合并。
- 不同知识点证据独立。
- 前置知识推荐有实际依据。
- 只有帮助后的正确不能当作独立成功。
- 单元复习后产生新的学习证据。
- 新证据可以更新原有复习推荐。
- 教师可以追溯原始作答。

# 十一、必须执行的三条完整流程

## 流程一：教师发布完整单元

管理员确认单元课时内容 → 教师搜索案例 → 生成并修改教案 → 保存版本 → 发布课时任务 → 多名学生收到任务 → 教师查看实际参与情况。

重点检查不同课时及版本的对应关系。

## 流程二：学生完整单元学习

学生从第一课开始 → 阅读讲解 → 完成天平互动 → 独立练习 → 进入第二课 → 遇到困难 → 选择提示与补基础 → 完成后续应用课 → 进入单元复习 → 提交独立检查 → 查看学习记忆。

重点检查跨课时状态恢复与知识点证据关联。

## 流程三：错误、补救与教师反馈

学生在应用题上答错 → 错题帮保存原始题目与解释 → 生成针对性补救 → 完成独立变式题 → 教师在学情中查看原始错误和新作答 → 安排补充教学 → 学生完成 → 教师回看并反馈。

不能将“提交说明”直接记录为独立复测成功。

# 十二、工程与数据安全要求

2. 所有测试只连接隔离数据库。
3. 不修改历史原始作答。
4. 不覆盖已发布课时版本。
5. 不删除上传文件。
6. 不把未核验答案自动判对。
7. 不自动发布模型生成的教案。
8. 不删除已有失败测试。
9. 不修改旧验收结论来满足本轮目标。
10. 不提交凭据、密钥和正式数据库备份。

部署环境未知时，必须先调查，不得擅自假设有服务器或域名。

# 十三、严格返修与停止规则

最多两轮实质性修复：

**第一轮：**

完成内容、流程和部署准备，执行初验。

**第二轮：**

集中修复已确认的P0/P1问题，重新运行相应测试及完整终验。

终验后：

- 核心验收全部通过、网站达到目标部署范围：第十六步完成。
- 数学内容有明确错误：不得正式发布对应课时。
- 单元课时缺失：不得标记完整单元上线。
- 关键师生流程失败：不得标记上线完成。
- 部署环境缺失：标记预发布完成、正式部署阻塞。
- 仅存在非阻断P2/P3：登记待办，不无限返修。

不能为让验收表变绿而降低标准。

# 十四、最终交付物

必须形成：

1. 第十六步完整单元内容清单。
2. 每课教学内容及数学审核记录。
3. 完整单元的课程及知识关系说明。
4. 教师备课与学生学习使用说明。
5. 第十六步35项统一验收表。
6. 三条真实师生业务流程记录。
7. 多课时真实指导和补救结果。
8. 原有功能回归日志。
9. 数据库升级及备份记录。
10. 部署说明。
11. 启动、更新和回滚步骤。
12. 实际运行环境验证结果。
13. 三种桌面宽度截图。
14. 未解决问题与阻塞清单。
15. README和当前进度更新。
16. 第十七步是否可以开始的判断。

最终汇报必须回答：

- 当前完整单元到底有哪些课时。
- 哪些课时已经正式审核与发布。
- 哪些内容是项目自编。
- 所有发布题目是否通过数学核验。
- 教师是否真的完成跨课时备课与发布。
- 学生是否真的完成多课时学习。
- 错题补救与学习记忆是否跨课时正确关联。
- 教师是否看到真实学情和反馈。
- 网站是否真实部署，访问范围是什么。
- 是否可以进入第十七步。

# 十五、Git交付约定

仓库 `AGENTS.md` 已记录用户对每步验收后提交和推送 `sczx/main` 的授权。

本轮遵循此约定：

1. 仅提交本项目源码、文档和必要验收证据。
2. 保留父级仓库其他项目的修改。
3. 不误推 `origin`。
4. 不强制推送。
5. 提交前检查远程历史。
6. 推送后核对远程main和项目文件树。
7. 用户若有更新的暂停指令，按最新指令执行。

**最终验收目标：交付一个教学内容完整、数学上可靠、师生能够连续使用、数据可以恢复、具备明确部署状态的一元一次方程单元。**

不要以首课的重复演示替代完整单元验收，也不要仅以生产构建成功宣布网站上线。
