# 一、最高优先级执行规则

以下规则必须严格遵守。

## 1. 先检查，再修改

开始工作后，首先执行：

- 检查 Git 当前分支、工作区状态、未提交修改。
- 检查最新提交及其相对上一版本的完整 Diff。
- 阅读项目整体规划、当前进度、第八步实施与验收文档、第九步规划及相关设计文档。
- 阅读第八步涉及的前后端完整调用链。
- 检查当前数据库结构、迁移、API、模型调用、前端交互和运行日志。
- 确认本地运行版本与 GitHub 最新版本是否一致。

本次审查基准提交：

`f3e2bac024c858c41b01ed4ae57a6a4a4c5a4583`

不能假设本地代码与该提交完全一致。

## 2. 严格限制返修次数

本次任务最多允许：

- 第一轮：完整审查、问题定位、制定修复计划。
- 第二轮：集中实施第八步修复及第九步开发。
- 第三轮：统一运行验收，根据失败项进行最后一次集中修复。

也就是最多进行两轮实质性修复。

第三轮验收后：

- 所有项目通过：结束开发。
- 部分项目不通过：明确标记未通过，列出原因和证据。
- 受外部服务、模型额度或运行环境影响：标记阻塞，说明阻塞条件。

禁止为了追求所谓完美反复重构已经通过的模块。

禁止每发现一个小问题就重新修改已经验收的模块。

禁止无明确收益的架构重写、组件重写和技术栈更换。

**验收通过后立即冻结本轮范围。其他改进统一放入后续待办，不得继续自行扩展。**

## 3. 严格区分事实和结论

所有测试必须记录：

- 实际执行的命令或浏览器操作。
- 实际执行时间。
- 实际测试数据。
- 实际输出结果。
- 是否通过。
- 对应日志、截图或测试文件。

禁止：

- 用代码静态检查代替功能测试。
- 用模拟响应代替真实模型调用验收。
- 用开发环境构建成功代替生产构建。
- 用截图代替交互测试。
- 用模型自己生成的正确性判断代替程序验证。
- 将小样本实验描述成真实教学效果。
- 将未执行的测试填写为通过。

# 二、阶段一：第八步全面复核与问题修复

## 2.1 第八步当前状态

第八步为「教学情境检索」。

当前实现包含：

2. 知识点正式名称与别名匹配。
3. 一层前置知识关系。
4. 年级、学科、知识点筛选。
5. 教学情境识别与权重调整。

8. 可选 Codex 重排。
9. 教师检索和学生学习指导接入。

请完整审查以上功能，重点检查实际业务调用是否正确。

## 2.2 必须重新审查的重点问题

### A. 检索算法与效果

当前已有 B0—B4 对比结果：

| 指标 | B0 | B3 |
|---|---:|---:|
| 全体 nDCG@5 | 0.8681 | 0.8669 |
| 全体 Recall | 0.8333 | 0.8125 |
| 测试集 nDCG@5 | 0.7514 | 0.9610 |

当前测试集只有：

- 4 篇案例。
- 14 条查询。
- 56 个相关性标签。
- 标签由 AI 拟稿，经用户单人复核。

需要重点检查：

1. 字段权重是否存在不合理的累加。
2. 知识点匹配是否存在过度加权。
3. 别名匹配是否会产生错误召回。
4. 一层前置知识是否会引入不相关案例。
5. 年级和学科筛选是否真正严格生效。
6. 情境识别失败时是否能安全退化。
7. 学生上下文是否会覆盖用户真实问题。
8. 空查询、无结果和负例查询是否正确处理。
9. 匹配解释是否与真实参与计算的字段一致。

特别注意：

当前 B3 在测试集上表现较好，但全体指标没有超过 B0。

不得通过反复修改权重、反复查看测试集结果来人为提高测试成绩。

需要保留 B0 作为原始基线，明确记录 B3 的实际收益和局限。

如果发现算法存在问题，可以修复，但必须通过独立测试证明修复的必要性。

### B. Codex 重排

目前 B4 的实际结果：

- 11 次模型调用。
- 9 次成功。
- 2 次降级。
- 实际指标没有超过 B3。
- 平均耗时约 20.9 秒。
- P95 耗时约 47.6 秒。

本次要求：

1. 检查重排调用、超时和错误处理。
2. 检查重复 ID、未知 ID、缺失 ID 的处理。
3. 检查模型失败后是否完整保留原排序。
4. 检查模型输出是否会错误丢失候选案例。
5. 检查是否存在不必要的重复模型调用。
6. 检查异步任务刷新、恢复及失败状态。
7. 默认继续关闭重排。

只有在有明确指标收益、可接受时延和可靠降级机制的情况下，才考虑调整默认配置。

不能为了展示 Agent 能力而强行增加重排调用。

### C. 知识点及版本管理

重点检查：

- 知识点正式名称重复。
- 别名重复。
- 别名与其他知识点正式名称冲突。
- 前置知识循环依赖。
- 前置知识点不存在。
- 非法数据类型是否会导致 500。
- 空值、NULL 和历史数据兼容。
- 保存后刷新是否正确恢复。
- 已发布案例是否会被草稿修改污染。
- 已发布课程及学生任务快照是否保持不变。
- 撤回、修订和历史版本检索是否正确。

特别检查 `save_knowledge` 对未经信任的请求体进行类型验证的完整性。

无效请求应返回明确的 4xx 错误，不能因列表、ID 或依赖关系的数据类型异常产生未处理的 500。

### D. 教师检索与学生指导

重点检查：

- 教师检索条件与后端实际查询一致。
- 切换检索条件时，旧请求不会覆盖新结果。
- 检索结果与案例版本一致。
- 匹配依据可以追溯到真实原文。
- 学生当前题目能正确传递给学习助手。
- OCR 识别文本以用户确认后的内容为准。
- 不同题目之间不能串用历史上下文。
- 刷新页面后任务状态可以恢复。
- 模型失败后可以正确重试。
- 用户编辑的内容不会被后台刷新覆盖。
- 求助记录、独立作答和教师回看保持一致。

重点检查 `ModelAssistant.vue`、`useModelJob.js`、`CheckLesson.vue`、`MaterialWorkbench.vue` 及相关 API。

对发现的并发请求、状态切换和历史任务恢复问题，必须通过实际复现验证。

### E. 工程质量

检查：

- 数据库迁移是否可以重复执行。
- 旧数据是否兼容。
- API 权限是否正确。
- 是否存在越权访问。
- 是否存在异步任务状态不一致。
- 是否存在前端未处理的异常。
- 是否存在无用依赖、重复逻辑和死代码。
- 是否存在生产环境构建问题。

为第八步核心功能补充可以长期运行的自动化回归测试。

不要只将测试脚本放在 `/tmp` 中。

优先使用项目已有测试框架；如果缺少测试基础设施，采用必要的最小方案，不引入庞大的测试体系。

## 2.3 第八步修复完成标准

# 三、阶段二：第九步——面向教学任务的 Agent 编排

## 3.1 第九步的目标

当前项目已经具备：

- 教学案例库。
- 原始教学材料。
- 课程和课时管理。
- 知识点及前置关系。
- 教师备课。
- 学生学习。
- 案例检索。
- AI 学习指导。
- 异步模型任务。

下一阶段需要解决的问题是：

**如何围绕一个真实教学任务，将已有的数据、检索能力和模型能力组织成一个有明确执行过程、可追溯、可验证的 Agent 工作流。**

请先阅读整体规划和现有系统，确定第九步的实际产品边界。

不能脱离已有系统单独开发一个聊天机器人。

不能仅仅在现有聊天框中增加一个 Agent 名称。

不能为了体现 Agent 概念，盲目增加多个互相调用的智能体。

## 3.2 设计原则

优先采用有边界的工作流编排。

建议重点考虑以下组成：

1. **任务理解**：识别教师提出的教学任务、目标、限制条件。
2. **上下文构建**：获取当前课程、课时、知识点、学生情况和相关材料。
3. **任务规划**：拆分为有限的执行步骤，明确每一步需要什么信息。
4. **工具选择**：根据任务调用现有检索、案例、材料和模型能力。
5. **结果生成**：生成符合教学场景的结构化结果。
6. **结果校验**：检查内容完整性、知识一致性、引用来源和任务要求。
7. **人工确认**：允许教师修改、接受或拒绝结果。
8. **任务保存**：将最终结果保存为草稿，供教师继续编辑。

以上是设计参考，具体实现必须结合现有架构确定。

## 3.3 首个可交付业务闭环

优先围绕教师备课场景，完成一条完整的 Agent 工作流。

示例：

教师提出：

「我要为七年级学生设计一节关于等式性质的教学活动，重点解决学生只会机械移项、无法理解两边共同运算的问题。」

系统需要：

1. 获取当前课程、课时和教学目标。
2. 识别涉及的知识点及前置知识。
3. 检索相关教学案例。
4. 检索相关原始教学材料。
5. 分析学生常见困难。
6. 制定教学活动和提问顺序。
7. 生成结构化备课建议。
8. 检查内容是否与当前教学目标一致。
9. 展示每个建议对应的案例、材料和原文依据。
10. 教师确认后保存为备课草稿。

最终结果应当能够继续进入现有的课时编辑、核对和发布流程。

不能自动发布课程或教学任务。

如果已有总体规划明确规定了其他第九步核心场景，应以项目规划为准，并选择最小、完整、可以验收的业务闭环。

## 3.4 Agent 工程约束

### A. 复用现有能力

优先复用：

- 当前 Codex CLI 模型调用。
- ModelJob 和 SSE 异步任务机制。
- 当前 BM25 检索。
- 材料解析和原文定位。
- 案例版本管理。
- 课程和知识点数据。
- 当前前端工作台。

不要擅自：

- 更换模型供应商。
- 部署本地模型。
- 引入 Qdrant 或其他向量数据库。
- 大规模更换技术栈。
- 重新实现已有的材料和案例管理。
- 为 Agent 创建一套重复的任务系统。

### B. 必须具备明确的执行边界

Agent 必须具备：

- 明确的任务输入。
- 有限的执行步骤。
- 明确的工具调用白名单。
- 单步骤超时。
- 总任务超时。
- 有限重试。
- 失败降级。
- 可追溯的执行日志。
- 结构化最终结果。

建议将单次工作流限制在 6 个以内的主要执行步骤，最多允许一次重新规划。

如果任务缺少必要信息，应明确指出缺少什么。

禁止无休止地自主循环、重复检索或反复调用模型。

### C. 人工控制

必须遵守以下权限边界：

- 检索、阅读和分析可以自动执行。
- 教学内容生成可以自动执行。
- 修改现有正式课程必须经过教师确认。
- 发布和撤回必须经过教师确认。
- 不得自动修改已发布历史版本。
- 不得将 AI 生成的内容标记为教师已经审核。
- 不得伪造材料来源和引用。

### D. 结果可解释

教师需要能够查看：

- Agent 接收了什么任务。
- 当前使用了哪些上下文。
- 执行了哪些步骤。
- 每一步调用了什么工具。
- 参考了哪些案例和材料。
- 哪些内容来自模型生成。
- 哪些内容经过程序校验。
- 哪些内容仍需教师确认。

不能只显示一个最终生成的大段文本。

### E. 异常与恢复

必须覆盖：

- 模型超时。
- 模型返回格式错误。
- 检索没有结果。
- 原始材料尚未解析。
- 部分步骤成功、部分失败。
- 用户刷新页面。
- 用户离开当前页面。
- 用户重复提交。
- 任务执行过程中服务重启。

任务不能因为一个非关键工具失败就直接丢失全部已完成结果。

# 四、第九步前端交互要求

界面必须符合现有师承智学的设计体系。

重点检查：

1. Agent 任务入口是否自然。
2. 教师是否能明确知道当前任务执行到哪一步。
3. 执行中是否有清晰的状态反馈。
4. 是否能展开查看每一步的执行结果。
5. 引用来源是否可以直接查看。
6. 最终结果是否方便修改。
7. 是否可以单独重新生成某个部分。
8. 是否能够保存草稿。
9. 是否存在失败、重试和取消入口。
10. 是否与现有备课流程保持一致。

禁止设计成大量卡片堆叠的 AI 聊天界面。

优先采用清晰的工作流布局：

- 左侧：教学任务和上下文。
- 中间：执行过程及结构化结果。
- 右侧：参考材料、案例依据和校验信息。

具体布局以现有页面和设计规范为准。

必须进行真实浏览器交互验收。

至少测试：

- 1440px。
- 1920px。
- 2560px。

检查页面溢出、滚动、布局比例、长文本、加载状态和异常状态。

截图必须来自实际运行的应用，不能用设计稿代替。
