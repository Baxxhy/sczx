# un-design

> Avoid unnecessary secondary labels and descriptions. Let the layout do the explaining.

让用户直接看懂对象、归属、主次和下一步。
以任务是否清楚为准，不设删字比例。

## 判断文案是否必要

对每段辅助文案，问：**删掉后，用户会失去什么？**

| 失去的内容 | 动作 |
| --- | --- |
| 没有新增信息，只是重复标题或按钮 | 删除 |
| 对象之间的归属、顺序或主次 | 先修布局，再判断能否删除 |
| 每个条目重复的同一上下文 | 提到共同标题、表头或分组 |
| 名称、选项差异、单位、限制或操作后果 | 保留，改成最短的准确表达 |

信息暂时用不到，且不会影响当前决定时，再考虑按需展开。
用户操作前必须知道的条件，放在操作发生处。

## 让布局承担解释

先确认用户任务、主要对象和主操作。
沿用项目的组件、排版和间距规则。

- 用邻近关系表达归属。组内间距小于组间间距。
- 用字号、字重和位置建立阅读顺序。
- 用稳定的行列和对齐支持比较。
- 同一上下文只说明一次。列表可共用标题或表头。
- 将操作放在它作用的对象旁边。
- 用准确的动词命名按钮，减少按钮下方的操作说明。

新建界面时，不给每个区块默认配上眉题、副标题和介绍。
只有标题或内容无法表达任务信息时，才添加说明。
若分组仍有歧义，补回明确名称。

## 保住理解所需的信息

- 保留字段名称、明确的操作名称和有意义的分组标题。
- 保留格式要求、单位、费用、选项差异和操作后果。
- 保留错误原因、恢复动作和必要的空状态引导。
- 陌生功能需要解释时，在首次使用处提供短说明。
- 图标含义不明确时，使用文字标签。

表单字段默认使用持续可见的标签。
不要用 placeholder 替代字段标签。
视觉上下文已明确命名控件时，仍保留可访问名称。
用原生语义结构表达标题、列表、表格和表单关系。
仅靠留白、颜色或屏幕位置表达关系不够。
必要说明不能只在鼠标悬停时出现。

## 常见取舍

| 原界面 | 精简方式 |
| --- | --- |
| “项目”下面写“在这里查看和管理你的项目” | 保留“项目”和项目列表 |
| “上传文件”按钮下写“点击按钮上传文件” | 删除重复说明 |
| 每张任务卡都写“状态：进行中” | 状态列共用表头，卡片保留具体状态 |
| 同一列表的每行都重复“创建时间” | 使用共同表头，保留每行日期 |
| 上传处写“PNG、JPG，最大 10 MB” | 保留，这是选择文件前的限制 |
| 删除确认写“同时删除 12 个文件，无法恢复” | 保留，这是决定操作所需的后果 |

删除文字后若需要更多图标、边框或装饰才能补回含义，重新检查分组与命名。
停止在任务已经清楚的位置，避免扩成整页重设计。

## 验证与交付

已有界面以相同数据、状态和视口对比前后。
检查用户是否仍能识别对象、定位操作并区分选项。
新建界面直接检查这些任务。

能运行页面时，查看实际渲染，并检查窄屏和长文本。
修改触及空状态、错误或已填写表单时，检查对应状态。
代码改动时，核对语义结构、可访问名称和阅读顺序。
只有截图时，说明视觉判断的范围，不声称已验证交互或可访问性。

审查任务给出具体删改建议；实现任务交付局部改动。
简要说明删掉了什么、布局承担了什么、保留了什么以及验证范围。

## 依据

- [NN/g：Aesthetic and Minimalist Design](https://www.nngroup.com/articles/aesthetic-minimalist-design/)：减少与当前任务无关的信息，保留完成任务所需的内容。
- [W3C WAI：Labeling Controls](https://www.w3.org/WAI/tutorials/forms/labels/)：控件名称应清晰，并与控件正确关联。
- [W3C WAI：Info and Relationships](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html)：视觉关系应能通过语义结构读取。
